# DC Comics Character Network

This repository contains the Python scripts used to collect DC Comics data from DC Fandom, extract character appearances, construct a character co-appearance network, and analyse its evolution over time.

The network is built from characters appearing in the same story. Each character is represented by a node, and an undirected edge is created between every pair of characters appearing in that story. Repeated co-appearances are recorded as edge weights.

The pipeline includes data collection, entity classification, manual cleaning, network construction, publication-year corrections, and network analysis.

## 1. Requirements

The project uses Python 3 and the following main libraries:

```bash
pip install pandas numpy scipy beautifulsoup4 lxml selenium webdriver-manager duckdb networkx matplotlib
```

The scripts also use standard Python libraries such as `csv`, `sqlite3`, `pathlib`, `re`, and `collections`.

Selenium is used to collect data from DC Fandom. The remaining processing and analysis scripts work with locally stored files.

Most scripts contain a `PROJECT_ROOT` or `PROJECT` variable that needs to be updated to match the location of the repository on the computer where they are executed.

## 3. Pipeline

The scripts should be run in the following order:

| Step | Script | Purpose |

| 1 | `comics_scrapper.py` | Collect comic titles and URLs |
| 2 | `download_comics.py` | Download the HTML pages for individual comics |
| 3 | `characters_url.py` | Collect character names and URLs |
| 4 | `Keywords_groups.py` | Collect reference lists for associations and other non-character entities |
| 5 | `dc_character_scraper_v3.py` | Extract and classify character appearances |
| 6 | `edge_v3.py` | Construct the dated character co-appearance network |
| 7 | `add_years.py` | Add manually verified publication years, if necessary |
| 8 | `year_manually.py` | Apply further publication-year corrections, if necessary |
| 9 | `comics_years_age.py` | Calculate network sizes from story appearances and prepare the DuckDB database |
| 10 | `network_size.py` | Calculate network sizes from the yearly edge lists |
| 11 | `assortativity_degree_chrono.py` | Analyse degree assortativity as comics are added chronologically |

Steps 7 and 8 are optional. If all the necessary publication years are available after running `edge_v3.py`, both scripts can be skipped and the paths for the following scripts have to be fix.

The network analysis scripts should use the latest available network, whether that is the original output from `edge_v3.py` or a version with manually corrected publication years.

## 4. Data collection

### 4.1 `comics_scrapper.py`

This script uses Selenium to collect comic titles and URLs from the DC Fandom `Category:Comics` page.

It collects the comics listed directly in the category. Comics contained only in subcategories are not necessarily included.

The resulting CSV is placed in the `data` folder and used by `download_comics.py`.

**Output:** `data/dc_comics.csv`

### 4.2 `download_comics.py`

This script reads the comic URLs collected in the previous step and downloads the corresponding HTML pages.

The HTML files are saved locally so that the following scripts can extract information without repeatedly requesting the same pages from DC Fandom.

Existing HTML files are skipped, allowing interrupted downloads to be resumed without downloading everything again.

**Input:** `data/dc_comics.csv`

**Output:** Downloaded comic HTML files.

The downloader and subsequent processing scripts must reference the same HTML directory. In the reviewed versions, some scripts use `data/comic_pages/` and others use `comic_pages/`.

### 4.3 `characters_url.py`

This script collects character names and URLs from DC Fandom's `Category:Characters`.

The resulting dataset is used as a reference when classifying the entities extracted from comic pages.

Duplicate character URLs are removed.

**Output:** `data/dc_characters.csv`

### 4.4 `Keywords_groups.py`

This script collects reference lists of entities that should not be treated as individual characters, including associations, teams, races, and other categories.

The category to be collected is selected by changing:

```python
CATEGORY_NAME = "..."
CATEGORY_URL = "..."
```

The script can be run for different categories to build the reference dataset.

Records are deduplicated using the combination of keyword and URL:

```python
drop_duplicates(subset=["keyword", "url"])
```

This allows identical keywords with different URLs to remain separate observations.

**Output:** `data/keywords_associations.csv`

## 5. Character extraction and cleaning

### 5.1 `dc_character_scraper_v3.py`

This script processes the downloaded comic HTML files and extracts the entities listed in the character appearance sections of each story.

The recognised sections include Featured Characters, Supporting Characters, Antagonists, Other Characters, Main Characters, Guest Characters, and Characters.

The extracted entities are compared against the character and association reference datasets to help classify each observation.

The classifications distinguish characters from associations and other entities. The resulting dataset retains information about the comic, story, entity, source URL, and classification.

**Main output:**

`data/scraper_v3/comic_characters_cleaned.csv`

The script also produces audit information used to identify observations requiring review.

### 5.2 Manual classification

After running the scraper, the classification results are reviewed manually.

This is an important part of the pipeline because DC Fandom appearance sections can contain organisations, locations, objects, and other entities alongside characters.

The manual cleaning is performed directly in:

`data/scraper_v3/comic_characters_cleaned.csv`

The `entity_kind` field is corrected where necessary. The network construction script subsequently uses the following classifications:

- `character`
- `external_url`
- `manual_review`
- `unknown`

In the cleaned dataset, observations retained under these four categories have been checked to ensure that they correspond to characters.

The classification labels alone should not be considered sufficient to establish character eligibility when processing new, unreviewed data.

A copy of the automatically generated CSV should be preserved before manual editing, since rerunning the scraper may overwrite the corrections.

## 6. Network construction

### 6.1 `edge_v3.py`

This script constructs the character co-appearance network from the cleaned dataset.

Characters appearing in the same story are connected through undirected edges. For a story containing n characters, the number of possible character pairs is:

n(n-1)/2

If the same pair appears in multiple stories, the observations are aggregated rather than creating duplicate edges in the final network.

The script also extracts publication dates from the downloaded HTML files and associates the available years with the network observations.

**Inputs:**

- `data/scraper_v3/comic_characters_cleaned.csv`
- Downloaded comic HTML files

**Output folder:** `network_dated_original_identity_test/`

The main outputs are:

| File | Description |
| `network_build.sqlite` | SQLite database containing the network data |
| `nodes.csv` | Character IDs, labels, classifications, and appearance information |
| `edges.csv` | Aggregated character pairs across the network |
| `edges_by_year.csv` | Character pairs aggregated by publication year |
| `story_appearances.csv` | Character appearances by story |
| `comic_dates.csv` | Publication dates and their sources |

### 6.2 Character identities

The script uses a conservative approach to identifying characters.

Where a recognised DC Fandom URL and universe designation support a stable identity, the character's URL path is used as its node identifier.

Otherwise, the script constructs an identifier using the source comic, story, and character name:

unknown::source_file::story::name

This prevents characters with identical names but potentially different identities from being automatically merged.

The approach may produce separate nodes for characters that are actually the same individual, but avoids introducing unsupported identity matches.

### 6.3 Mentioned-only characters

The script includes the setting:

INCLUDE_MENTIONED_ONLY = True

This controls whether mentioned-only characters are included in the network.

Setting it to `False` excludes these observations. The two settings can be used to generate separate network versions for comparison.

Each version should be saved in a different output directory.

## 7. Manual publication-year corrections

The scripts and CSV files used for additional date cleaning are stored in:

Cleaning and extra steps/
    add_years.py
    year_manually.py
    year_manual.csv
    extra_years.csv

These scripts are only necessary when publication years are missing from the dataset generated by `edge_v3.py`.

After constructing the network, `comic_dates.csv` should be checked to identify comics without a publication year.

If no years are missing, the network can be used directly for analysis.

### 7.1 `add_years.py`

This script applies publication years that have been identified and verified manually.

The corrections are stored in `year_manual.csv`.

The script attempts to match the manual records to comics in the database using source identifiers and filename matching.

It updates a copy of the SQLite database rather than modifying the original. Publication years already present in the database are preserved, and unresolved corrections are reported for further checking.

The corrected network files are then exported again.

**Input:** `Cleaning and extra steps/year_manual.csv`

**Output:** `network_dated_original_identity_years_added/`

### 7.2 `year_manually.py`

This script is used if additional publication years can still be identified after running `add_years.py`.

The remaining corrections are stored in `extra_years.csv`, using the columns:

source_file,publication_date

Unlike the previous correction script, this one requires an exact match between the `source_file` identifier in the CSV and the corresponding database record.

It also checks that the comic does not already have a publication year.

If any correction cannot be validated, the script stops before updating the database.

**Input:** `Cleaning and extra steps/extra_years.csv`

**Output:** `network_dated_final/`

The output contains the corrected SQLite database, updated network CSVs, and `extra_year_audit.csv`.

The script reports the number of comics that remain undated. It does not automatically assign dates to observations that could not be verified.

Both correction scripts are optional. It is possible to run neither, only the first, or both, depending on the number of missing dates and the corrections available.

## 8. Network analysis

The analysis scripts examine the network over the full period, by comic-book age, and by individual publication year.

The following periods are used:

| Age | Years |
| Platinum | 1935–1937 |
| Golden | 1938–1955 |
| Silver | 1956–1969 |
| Bronze | 1970–1985 |
| Iron | 1986–2010 |
| Modern | 2011–2026 |

These boundaries are defined in the scripts and can be changed if necessary.

### 8.1 `comics_years_age.py`

This script calculates network sizes using the character appearances recorded at the story level.

It reads `nodes.csv` and `story_appearances.csv`, then reconstructs character pairs by joining characters that appear in the same story.

The resulting pairs are aggregated first by comic and then by year.

DuckDB is used to process the data and calculate the number of nodes and edges for the overall network, each comic-book age, and each individual year.

**Inputs:**

- `nodes.csv`
- `story_appearances.csv`

**Working database:**

`network_analysis_v3.0/network_comics_work.duckdb`

The database includes the `pair_comic` and `pair_year` tables.

The results are printed to the terminal. The working DuckDB database is also used by `assortativity_degree_chrono.py`.

### 8.2 `network_size.py`

This script calculates network sizes using the previously constructed `edges_by_year.csv` rather than rebuilding character pairs from story appearances.

It uses DuckDB to aggregate the edges and calculate the number of distinct nodes and edges across the same periods.

**Inputs:**

- `nodes.csv`
- `edges_by_year.csv`

### 8.3 `assortativity_degree_chrono.py`

This script analyses how degree assortativity changes as comics are added to the network.

It reads the `pair_comic` table generated by `comics_years_age.py` and constructs a cumulative NetworkX graph.

The age to analyse is selected using:

AGE = "Platinum"

The available options are Platinum, Golden, Silver, Bronze, Iron, and Modern.

The graph starts empty at the beginning of the selected age. Comics are added sequentially, and after each comic the script calculates:

- Number of nodes
- Number of edges
- Degree assortativity
- Node-strength endpoint correlation
- Mean and variance of endpoint degrees

When an edge already exists, its weight is increased by the additional co-appearance evidence.

The script produces plots of assortativity against network size and publication year. It also generates a visualisation of the final network and a complementary cumulative degree distribution.

For the network visualisation, it uses the GC and displays up to 2,000 of its highest-degree nodes. The degree distribution and top-20 ranking are calculated from the complete largest connected component.

#### Ordering of comics

Comics are added in ascending publication-year order.

When several comics have the same publication year, they are ordered alphabetically by their source filename.

This produces a reproducible sequence, although it does not necessarily correspond to the exact order in which comics were published within a year.

The ordering can affect intermediate assortativity values. It does not affect the final network obtained after all comics from the selected age have been added.

The current script uses this alphabetical ordering as a baseline. A possible improvement would be to use exact publication dates where available or randomise the order of comics within each year over multiple simulations to examine how sensitive the results are to the order of addition.

The script currently analyses the co-appearance network. A separate analysis would be needed for relationships supported by synopsis evidence.

## 9. Running the pipeline

After setting the correct paths, the scripts can be executed individually.

```bash
python comics_scrapper.py
python download_comics.py
python characters_url.py
python Keywords_groups.py
python dc_character_scraper_v3.py
```

The character classifications in `comic_characters_cleaned.csv` must be reviewed before constructing the network.

`edge_v3.py`


Check `comic_dates.csv` for missing publication years.

If manual corrections are available, run the relevant scripts:

`Cleaning and extra steps/add_years.py`
`Cleaning and extra steps/year_manually.py`


These commands are optional and should only be run when the corresponding correction files contain records that need to be applied.

Once the final network has been selected, update the analysis input paths and run:

`comics_years_age.py`
`network_size.py`
`assortativity_degree_chrono.py`

`comics_years_age.py` must be run before `assortativity_degree_chrono.py` because the latter uses its DuckDB working database.

The analysis scripts use fixed input and output paths. These should be checked before execution, especially if the optional publication-year correction stages were skipped.

## 10. Notes and possible improvements

The main points to consider when extending the pipeline are:

- **Data coverage:** The collection scripts use DC Fandom category listings, which may not include every comic or character.
- **Manual classification:** Character classifications should be reviewed whenever new data is collected.
- **Character identities:** The current method avoids uncertain identity merges but may represent the same character under multiple identifiers.
- **Comic ordering:** The chronological assortativity analysis currently uses alphabetical filename ordering within each year. Exact dates or repeated randomised ordering could provide a more robust comparison.
- **Computational performance:** Recalculating assortativity after every comic can be expensive for larger datasets. Less frequent checkpoints may be useful for larger experiments.

The scripts currently use local file paths and are intended to be run sequentially rather than through a single automated pipeline. Before running the project on another computer, the paths should be updated and the input/output directories checked.
